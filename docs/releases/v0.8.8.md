Version `0.8.8` is the patch release for [Issue #58](https://github.com/wheakerd/axiom/issues/58). It removes contradictory public measurements and Git routing claims by binding every managed rendering to one reviewed source of truth.

## Exact Draft Evidence Validation

The unchanged `Publish immutable release` contract accepts exactly one draft named `Axiom v0.8.8` at the GitHub-signed `main` commit. The draft starts with one content-addressed 17-case Codex observation, and the repository-owned validator binds its filename, digest, size, version, tag, commit, tree, response schema, ordered cases, and zero-regression gates before publication. The workflow then emits and revalidates one deterministic attestation, publishes the exact draft as immutable and GitHub Latest, and fails closed on a missing, duplicated, mutable, or mismatched Release.

## Canonical Release Facts

The versioned `evals/context-budget/results/v<version>.json` records are the sole measured-facts source. The standard-library renderer keeps README bound to the current manifest version, requires the current release note to be managed, and continues validating every marker-managed historical release note against its own immutable versioned record.

The corrected v0.8.4 public rendering now reports 7,739 UTF-8 bytes, 1,001 whitespace-delimited words, 135 logical lines, one direct reference, and an estimated 1,935 tokens. Its cumulative deltas from immutable v0.7.9 are +1,840 bytes, +244 words, +28 lines, zero references, and +460 estimated tokens; both review thresholds remain reached and reviewed.

Static counts remain explicitly labeled context proxies, token values remain `ceil(UTF-8 bytes / 4)` estimates for the same English Markdown surface, and generated documentation cannot promote `NOT-RUN` or `UNAVAILABLE` host evidence.

## Structured Git Route Boundary

The human-reviewable `axiom_validation/route-boundaries-v1.json` catalog now owns the Git selection boundary shared by the startup gate, README, v0.8.4 release note, and ten directly generated offline fixtures.

- Ordinary named-remote non-force staging, commits, and pushes without a tag or traceable trigger remain host-native.
- A combined commit, tag, and push of an already-prepared plugin release selects the hardened `traceable-git-submit` phase.
- Explicit `$traceable-git-submit`, checkpoint, baseline, consolidation, recovery, multi-target, force, and history-replacement requests remain traceable.
- Merely mentioning submit, publish, or push does not select the route.

## Drift Detection And Validation

`scripts/render-release-facts.py --check` is read-only and fails when managed documentation differs from its versioned record or route catalog. The explicit `--render` mode updates only managed marker regions. The aggregate publication guard runs both checks in pull requests and on pushes.

Negative fixtures reject a changed measured value, restoration of the over-broad Git sentence, an unlabeled superseded v0.8.4 candidate, and a historical label without a full immutable commit or content SHA-256 identity.

The 104-test suite, publication guard, distribution drift guard, canonical-facts check, JSON parsing, English-only scan, and Claude Code strict plugin validation pass on the candidate tree. The local Codex plugin validator retains its documented stale-schema conflict for supported `hooks`, `brandColorDark`, and `supportURL`; those fields are intentionally unchanged.
