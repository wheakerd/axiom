# Axiom v0.4.2

Released: 2026-08-12

Version `0.4.2` fixes the review boundary used when AGENTS Architect receives a
first durable instruction update request after ordinary work. The workflow now
reviews the task from its oldest available turn instead of treating the latest
phase, an earlier AGENTS read, or Skill activation as an implicit baseline.

The immutable Git tag `v0.4.2` identifies this release. The moving `latest`
Git tag and GitHub's Latest Release marker are synchronized to the same release
commit; consumers that need a stable identity should use `v0.4.2`.

## Highlights

### Whole-task first review

On the first `effective-instructions` or preview review in a task, AGENTS
Architect establishes a review window from the oldest available turn through
the trigger message. A request made after implementation, validation, or
publication therefore still evaluates the earlier completed phases for durable
candidates and retrieval friction.

Task and thread inspection pages backward until that boundary is reached.
Turn summaries, user corrections, material file changes, and final outcomes
provide coverage; raw tool output is included only when needed to decide or
verify a candidate.

### Explicit incremental baselines

A later review may begin after an earlier one only when the completed review
recorded its start, reviewed-through point, and candidate dispositions.
Unresolved preview candidates carry forward.

Reading AGENTS, making a narrow AGENTS edit, completing ordinary work, or
activating AGENTS Architect does not create an incremental baseline. When the
required older history is unavailable, the workflow reports that limitation
instead of claiming a complete task review.

### Coverage-aware application and reporting

Maintenance now confirms that context evidence reached the review-window
boundary before applying a task-context update. A newest-phase-only extraction
cannot be presented as a complete review.

Review coverage and accepted-rule count remain independent. A complete review
may still produce one small canonical update or no file change because
temporary, duplicated, unsupported, and one-off candidates remain rejected.

## Compatibility and package shape

- Both plugin manifests declare version `0.4.2` and point to `./skills/`.
- The direct public Skills remain `using-axiom`, `agents-architect`,
  `optimize-codex-usage`, `traceable-git-submit`, and
  `reversible-system-change`.
- Codex and Claude Code retain separate manifests, marketplace descriptors,
  and hook files over the same Skill source.
- No hook command, startup route, skill identifier, runtime dependency,
  service, telemetry path, or automatic updater was added.

## Release validation

The release candidate was checked from the repository and, for validators that
could write, from a disposable copy outside the publishable tree. The recorded
workflow verified:

- distribution agreement among the Skill tree, both manifests, both
  marketplace wrappers, and the README shared-skill list;
- publication invariants for required files, JSON structure, manifest version
  agreement, exact hook shapes, documented hook commands, Markdown links,
  frontmatter, reference discovery, and packaged Skill layout;
- static routing contracts, rollback gates, JSON and YAML parsing,
  English-only public definitions, instruction-size limits, whitespace, and
  absence of private or generated artifacts;
- all five packaged Skills with the local Skill Creator quick validator;
- strict Claude Code `2.1.220` plugin validation; and
- the complete reported task-history scenario plus incremental-baseline and
  narrow-edit controls against the checked-in review-window contract.

Codex CLI `0.147.0` does not expose a plugin-validation command. The bundled
local `plugin-creator` validator rejects the Codex manifest's intentional
`hooks` field even though Axiom's checked-in wrapper and publication validator
require it. This remains a validator discrepancy, not a pass.

The task-history scenarios exercise the checked-in decision contract. They do
not prove that every fresh host model will make the same semantic selection.

## Known limits

- A full review evaluates all available turns but does not persist every
  implementation detail or replay every raw tool output.
- Mutable source, diffs, runtime state, and concrete change impact still
  require current direct inspection.
- Compacted or unavailable history must be reported and cannot be represented
  as a recovered full conversation.
- Existing installations and sessions may retain `0.4.1` until the user
  explicitly refreshes and starts a new session.
- The moving `latest` tag is a convenience alias, not an immutable source
  identity.
