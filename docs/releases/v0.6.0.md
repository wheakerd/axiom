# Axiom v0.6.0

Released: 2026-08-18

Version `0.6.0` adds an explicitly user-triggered reconciliation workflow for
checking existing AGENTS guidance against current implementation. It keeps
ordinary maintenance unchanged, treats execution discontinuities as evidence
rather than triggers, and requires independent audits before one isolated
writer may update the instruction system.

The immutable Git tag `v0.6.0` identifies this release. The moving `latest`
Git tag and GitHub's Latest Release marker are synchronized to the same release
commit; consumers that need a stable identity should use `v0.6.0`.

## Highlights

### Explicit preview and apply modes

`effective-instructions:reconcile-preview` performs a read-only comparison.
`effective-instructions:reconcile` permits only evidence-backed edits to the
identified AGENTS system. Both may begin in a fresh session, and ambiguous
natural-language requests require clarification before a mode is selected.

Ordinary AGENTS updates remain on the normal maintenance route. Repository
drift, rollback, partial execution, compaction, model or agent handoff, and
approval-review discontinuities do not activate reconciliation by themselves.

### Live implementation baseline

The live filesystem working tree is the default baseline. Material staged
divergence, unstaged changes, untracked paths, and ignored content are recorded
separately. A named ref is used only when the user selects it, and it cannot
hide a conflicting live tree.

### Evidence before deletion

Compound rules are split into independently decidable claims. The ledger keeps
claim kind, direct evidence, counterevidence, observed status, disposition, and
write action separate. Search misses and absent tests are bounded negative
evidence, not proof that a rule should be removed. Normative, authorization,
validation, routing, and source-of-truth rules retain their own evidence tests.

### Strict collaborative reconciliation

Both modes require one coordinator and independent instruction,
implementation, and provenance auditors. Everyone remains read-only during
the audit. After the ledger and target paths are frozen, exactly one
non-coordinator writer may apply the authorized AGENTS changes. Missing roles,
unresolved evidence, or uncertain writer isolation stops writes and is
reported as `NOT-RUN`.

## Compatibility and package shape

- Both plugin manifests declare version `0.6.0` and point to `./skills/`.
- The direct public Skills remain `using-axiom`, `agents-architect`,
  `optimize-codex-usage`, `review-axiom-task`, `traceable-git-submit`, and
  `reversible-system-change`.
- The new capability is routed inside `agents-architect`; it does not add a
  duplicate top-level Skill, executable harness, background process, or
  localized trigger table.
- Hook commands, marketplace paths, and installation commands are unchanged.
- The release adds no implementation-edit, commit, push, deployment,
  credential, telemetry, automatic-update, or background-work authorization.

## Release validation

The release candidate was checked from the repository and, for validators that
could write, from a disposable copy outside the publishable tree. The recorded
workflow verified:

- distribution and publication agreement for 19 required files, 6 JSON files,
  46 Markdown files, 15 routing scenarios, 10 rollback scenarios, both
  marketplace wrappers, release documentation, and version `0.6.0`;
- both manifests and marketplace descriptors, both declared hook files, exact
  documented hook commands, public links, frontmatter, reference discovery,
  packaged Skill layout, and synchronized version metadata;
- all six packaged Skills with the local Skill Creator quick validator;
- Claude Code `2.1.220` strict plugin validation, English-only public definitions,
  instruction-size limits, whitespace, and absence of private or generated
  artifacts; and
- focused reconciliation scenarios covering both canonical modes, explicit
  non-English normalization, ordinary-update and discontinuity no-trigger
  controls, live-tree versus `HEAD`, partial rollback, bounded negative
  evidence, normative constraints, worker conflict, active-chain authority,
  preview/apply isolation, and missing-role stops.

The bundled local `plugin-creator` validator rejects the Codex manifest's
intentional `hooks` field on both the clean baseline and release candidate.
This remains a validator discrepancy, not a pass.

The static scenarios validate checked-in contracts. A fresh Codex or Claude
Code session-level semantic-routing check was not run and is not implied by the
repository checks.

## Known limits

- Reconciliation completeness depends on direct access to every scoped
  implementation and instruction owner that can change a conclusion.
- If the host cannot provide the required independent workers or isolate one
  writer, the workflow stops without applying changes.
- Current-session loaded instructions remain authoritative even when the audit
  identifies a correction for later eligible loads.
- Existing installations and sessions may retain `0.5.1` until the user
  explicitly refreshes and starts a new session.
- The moving `latest` tag is a convenience alias, not an immutable source
  identity.
