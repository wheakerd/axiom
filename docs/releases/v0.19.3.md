# Axiom v0.19.3

Version `0.19.3` states the host permission boundary in the always-loaded startup routing gate `plugin/skills/using-axiom/SKILL.md` and in the two action owners, `plugin/skills/confirm-external-action/SKILL.md` and `plugin/skills/reversible-system-change/SKILL.md`, and adds the `plugin/skills/using-axiom/references/host-permission.md` reference that carries the rule and each host's labeled mechanics. Hooks and every manifest field other than the version are unchanged. The [runtime identity](../runtime-identity.md) owns the digest and policy revision.

## Why A Patch

Issue #193 observed that when a host permission mode stands between the model and a consequential action, Axiom gave no direction for the moment before the attempt or for the denial itself: the gate said only that a no-match result is not a denial and that a permission-bypass mode expands no authority. Work that runs host-native under no Axiom route is reached only by the always-loaded gate, so the boundary lives there. The [release standard](../runtime-identity.md#version-increment) classifies a boundary statement and a reference without a new route or capability as a patch.

## What Changed

- The gate's Boundaries gain one bullet: where a host mode may deny an action, present the exact action for the user's grant first; a denial is a stop, never a retry by another tool, flag or path; read `references/host-permission.md`.
- Three trims make room: the `local-web-search` entry loses the word "planned", the `optimize-agent-usage` entry loses the clause "preserve required quality and safety" that its own description already states, and the cross-route rule loses the parenthetical list of persistent changes that the `reversible-system-change` entry already enumerates. The sentence "each owner keeps its authority, write-set, rollback and verification gates" moves into `references/credential-lifecycle.md`, the reference that every explicit credential-lifecycle task already loads. Every selection anchor, the ordinary-Git no-route anchor, and the cross-route rule that authorization under either route never satisfies the other are unchanged.
- `references/host-permission.md` states the host-neutral boundary: the grant names one exact action and target and is what the host then evaluates, a denial is a stop and not evidence of a routing or repository-state conflict, no permission mode, approval policy, sandbox, hook trust, or other host setting is changed to make an action pass, and the stop and the granted scope are recorded in host-native task context.
- `confirm-external-action` names a host permission-mode denial among its stop conditions and points to the reference; `reversible-system-change` adds the same boundary to its safety rules.
- The Trust Model and Architecture pages describe the boundary; the Skill Reference and README are unchanged because no route or description changes.

## Host Mechanics

The reference labels each host plainly and maps neither host's settings onto the other. Claude Code 2.1.308 prompts natively in its standard permission mode, evaluates each call against the conversation in `auto` mode so a grant must name the exact action and target, and keeps `bypassPermissions` as the permission-bypass mode that `delegate-simple-task` already defines. Codex CLI 0.164.0 either asks the user when the model requests approval (`on-request`) or, with `never`, returns an execution failure to the model without asking; under the boundary that failure is presented to the user as the exact command and a stop.

## Limit

The boundary reduces unprompted attempts and workarounds. It does not make the host's decision predictable, it waives no host prompt, and it turns no grant for one action into a grant for another.
