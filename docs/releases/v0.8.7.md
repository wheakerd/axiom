## Exact Draft Evidence Validation

The manual `Publish immutable release` workflow runs only when the dispatch ref is the exact strict numeric SemVer input tag. It checks out that immutable tag commit without persisting credentials, resolves the local tag through `refs/tags/<tag>`, and reads the remote `refs/heads/main` and `refs/tags/<tag>` objects through their fully qualified GitHub Git-reference endpoints. The tag must be one lightweight ref to the checked-out commit, the commit must remain on live `main` history, and `main` must still equal it immediately before any publication mutation. REST and GraphQL must independently report a valid GitHub-made signature for the release commit.

The workflow intentionally retains only `contents: write`. It no longer calls the repository immutable-release settings endpoint with `GITHUB_TOKEN`, because that endpoint requires repository Administration read permission that the workflow token cannot receive. The release operator must read back `enabled: true` with an owner credential immediately before dispatch. The workflow then proves the outcome from the exact final Release rather than treating the operator preflight as final evidence.

The workflow uniquely selects one authenticated Release-list entry named `Axiom v0.8.7`, freezes its numeric Release ID, and uses only ID-addressed reads, uploads, publication, and bounded cleanup after selection. The draft starts with exactly one uploaded `axiom-v0.8.7-codex-core-v2-<full-sha256>.json` observation. The repository-owned validator checks the downloaded bytes, filename digest, GitHub digest, size, asset identity, exact version, tag, commit, tree, response schema, fixed 17-case order, and all existing zero-regression gates.

## Durable Attestation And Immutable Publication

The workflow emits one deterministic content-addressed attestation that binds the frozen Release, subject, release-notes digest, observation asset, and validator result. It uploads the attestation only when absent, downloads both remote assets by frozen asset ID, and revalidates them before publication. An exact interrupted draft or already-immutable final Release remains recoverable without replacing either asset.

After the draft is published as GitHub Latest, the workflow reads the same Release ID and classifies only an exact tag, commit, published-state match as `immutable` or `mutable`. An exact `immutable=true` result proceeds to full final verification. An exact `immutable=false` result triggers bounded compensation: delete only that frozen mutable Release ID, list all Releases again, prove that neither its ID nor tag remains, and fail. Malformed, ambiguous, or mismatched state fails closed without choosing a deletion target. Cleanup re-reads the Release immediately before deletion, then rechecks the protected tag, signed commit, main-history relationship, and stable Latest boundary after absence is proven. Repository-global publication concurrency supplies the workflow's single-writer boundary.

Final verification still requires:

- `draft=false`, `prerelease=false`, and `immutable=true`;
- the frozen Release ID, tag, target commit, title, notes digest, observation asset, and attestation asset;
- unchanged downloaded bytes and API digests; and
- the GitHub Latest endpoint to identify v0.8.7.

The protected Git tag is never deleted by compensation. If immutable publication succeeds but a later check fails, the Release is not mutated; recovery is read-only and any genuine defect requires a later SemVer fix-forward.

## Provenance And Dispatch Repair

`Release signature guard` now accepts an explicit manual dispatch on one exact `refs/tags/v<major>.<minor>.<patch>` ref. It binds that tag to the matching manifest version, requires the target on `main` history, and verifies a valid GitHub-made commit signature. Main and reviewed `release/v*` branch verification remain unchanged. This closes the previous mismatch between the documented post-publication exact-tag check and the workflow's manual-ref allowlist.

The publication workflow performs its own exact-ref and signature checks because ordinary events created with its `GITHUB_TOKEN` do not reliably start another workflow. After publication, the operator still dispatches the independent signature guard on `v0.8.7` and requires that exact-tag run to pass.
