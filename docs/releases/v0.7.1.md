# Axiom v0.7.1

Released: 2026-08-20

Version `0.7.1` closes two authorization-boundary gaps without adding a public
Skill or broadening an existing route. Traceable Git submission now freezes a
non-executable Git process boundary before every command, and reversible system
change now distinguishes read-only workflow rehearsal from an explicitly
authorized isolated restore rehearsal.

The immutable Git tag `v0.7.1` identifies this release. Consumers that need a
stable source identity should use that tag rather than a moving alias or
floating branch.

## Highlights

### Git inspection cannot silently execute target-controlled programs

`traceable-git-submit` treats repository and worktree configuration, includes,
attributes, hooks, helpers, filters, signing or transport programs, and ambient
Git process state as untrusted executable input. Before even a read-only Git
command, the workflow must establish a fixed process envelope, preserve literal
argument vectors, reject or neutralize command-bearing configuration, resolve
permitted executables independently of the target, and stop on drift.

Transport allowlists and endpoint secrecy remain required, but they are no
longer presented as sufficient protection against local configuration such as
`core.fsmonitor` or `core.sshCommand`. Publication scenarios exercise the
execution boundary across inspection, metadata, commit, and network phases.

### Rehearsal claims match their actual write authority

`reversible-system-change` now separates three phases: a read-only plan or
non-mutating workflow rehearsal, an independently authorized isolated restore
rehearsal, and the complete authorized system change. A generic request to
rehearse a deployment cannot imply persistent writes; it must remain read-only
or clarify which rehearsal type the user intends.

An isolated restore rehearsal may establish only the `rehearsed` evidence
label. It requires an exact non-active target, a frozen rehearsal write set,
proof that active state and data cannot be affected, and separate authority for
the rehearsal write. Candidate preparation, promotion, full execution,
rollback, and cleanup remain independent actions.

## Compatibility and package shape

- Both plugin manifests declare version `0.7.1` and point to `./skills/`.
- The seven direct public Skills remain `using-axiom`, `agents-architect`,
  `optimize-codex-usage`, `review-axiom-task`, `confirm-external-action`,
  `traceable-git-submit`, and `reversible-system-change`.
- Hook commands, hook paths, marketplace source paths, route identifiers,
  installed runtime dependencies, and GitHub Action pins are unchanged.
- The release adds no implicit edit, commit, push, deployment, credential,
  restore, promotion, cleanup, telemetry, update, or background-work authority.
- Existing `0.7.0` installations remain compatible; the host controls when a
  newer installed snapshot becomes active in a session.

## Release validation

The release candidate was checked from the repository and, for validators that
could write, from a disposable copy outside the publishable tree. The recorded
workflow verified:

- distribution and publication agreement for 22 required files, 6 JSON files,
  51 Markdown files, 28 routing scenarios, 37 traceable-Git security scenarios,
  12 external-action scenarios, 10 rollback scenarios, version `0.7.1`, and 2
  immutable Action pins;
- both manifests and marketplace descriptors, both declared hook files, exact
  documented hook commands, public links, frontmatter, reference discovery,
  packaged Skill layout, identity fields, lifecycle commands, and synchronized
  version metadata;
- all seven packaged Skills with the local Skill Creator quick validator;
- Claude Code `2.1.220` strict plugin and marketplace validation, English-only
  public definitions, instruction-size limits, whitespace, and absence of
  private or generated artifacts;
- focused Linux and Git `2.55.0` probes that reproduced target-controlled
  `core.fsmonitor` and `core.sshCommand` execution, blocked both paths under the
  protected envelope, and preserved benign `git status` behavior; and
- a complete security review of 71 artifacts across 10 attack surfaces with no
  remaining reportable finding, plus semantic regressions for generic,
  read-only, and exactly authorized isolated restore rehearsals.

The bundled local `plugin-creator` validator rejects the Codex manifest's
intentional `hooks` field on both the candidate and a clean prior release. This
remains a validator discrepancy, not a pass. Codex CLI `0.148.0` exposes no
native plugin-validation command.

The static scenarios validate checked-in contracts. A fresh Codex or Claude
Code session-level semantic-routing check, real installation, real external app
action, and real persistent system change were not run and are not implied by
the repository checks.

## Known limits

- Static source and scenario checks cannot prove model route selection in a
  fresh host session or the semantics of a connected service.
- Dynamic malicious-Git-configuration probes ran on Linux with Git `2.55.0`;
  other supported operating systems and Git versions still rely on the
  documented version-aware execution floor.
- Hosts that cannot preserve literal arguments, freeze a non-executable Git
  environment, or enforce no-follow metadata containment must stop rather than
  weaken the submission boundary.
- An isolated restore rehearsal remains a persistent write and therefore needs
  exact authority even though it cannot promote or modify the active target.
- The immutable `v0.7.1` tag, not a moving alias, is the stable release
  identity.
