# Axiom v0.7.9

Released: 2026-08-23

Version `0.7.9` closes the repository-governance visibility gap described in
[Issue #29](https://github.com/wheakerd/axiom/issues/29). It is a compatible
security-hardening release: installed skills, startup hooks, route behavior,
action authority, and runtime dependencies are unchanged.

The immutable Git tag `v0.7.9` will identify this release. Consumers that need
a stable source identity should use that tag rather than a moving alias or
floating branch.

## Security Boundary

GitHub rulesets are the server-side enforcement boundary for protected refs.
Repository workflows can validate a proposed tree, require evidence attached
to a target commit, or detect an invalid event after it occurs; documentation
and successful workflows cannot themselves prevent a ref mutation.

The new [Repository Governance](../repository-governance.md) document records a
read-only observation made on 2026-08-23 without changing GitHub settings. It
also preserves a manual minimum-permission procedure so future reviewers can
compare the documented policy with live state and report hidden fields as
unavailable.

## Observed Governance

The active `require-signed-commits-on-main` ruleset targets only
`refs/heads/main`. It requires a pull request, signed commits, squash merging,
and blocks non-fast-forward updates. It reported no bypass actors. It requires
zero approving reviews, does not require a code-owner review, contains no
required-status-check rule, and contains no explicit deletion rule. Those gaps
are documented rather than promoted to controls.

The active `require-github-signed-release-tags` ruleset targets
`refs/tags/v*`. It requires signed targets and the exact
`Verify GitHub-signed release target` check, blocks deletion, blocks
non-fast-forward updates, and reported no bypass actors. Its active deletion
and force-push restrictions prevent ordinary actors from deleting or replacing
an existing release tag. No destructive probe was performed.

The release-tag ruleset has no creation restriction or actor allowlist. The
complete effective creator roster is therefore `UNAVAILABLE`; actors with Git
write permission must still satisfy the signature and required-check rules.
The `repository-guards` check runs on pull requests and pushes but is not a
required `main` check as of the verification date.

## Critical-Path Ownership And Drift Checks

`.github/CODEOWNERS` now assigns `@wheakerd`, the repository owner, to every
Issue #29 critical path. It also covers the CODEOWNERS and governance files
themselves plus `axiom_validation/` and `tests/`, because the stable scripts
delegate policy decisions to those sibling paths.

The standard-library publication validator now requires both governance files,
checks the dated snapshot's exact facts, and requires the exact ordered
critical-path owner set. A focused negative test removes the validation-module
owner and verifies that the contract fails closed. This static check detects
checked-in drift; it does not query GitHub or prove current remote enforcement.

No scheduled or manually dispatched governance-audit workflow was added. The
ruleset API is already readable without administrative workflow permission for
this public repository, while bypass actors can be hidden from callers without
write visibility. Granting a workflow ruleset-write access merely to inspect
that field would weaken the minimum-permission boundary.

## Release Validation

The candidate is validated from a disposable copy outside the publishable
worktree. The local workflow covers:

- the focused repository-governance contract and its missing-sibling-owner
  negative case;
- distribution drift, compatibility evidence, publication policy, JSON,
  Markdown links, English-only documentation, package shape, and whitespace;
- the complete standard-library unit-test suite and repository-relative
  invocation; and
- direct diff review of every governance, ownership, validation, and release
  surface.

The local checks do not claim a GitHub pull-request run, merged-`main` run,
immutable-tag run, or GitHub Release event. Those are remote publication
evidence and remain `NOT-RUN` until the authorized release phase.

All 48 standard-library unit tests passed. The aggregate passed with 47
required files, 70 Markdown files, 47 routing cases, 13 fixed benchmark cases,
nine labeled host records, and 12 exact critical-path CODEOWNERS entries at
version `0.7.9`. Repository-relative aggregate invocation, JSON parsing,
distribution drift, compatibility evidence, English-only documentation, and
whitespace checks also passed.

Claude Code `2.1.220` strict marketplace and plugin validation passed in an
isolated configuration directory. This is an offline package signal, not an
authenticated host observation. Codex CLI `0.149.0` exposed no plugin-validation
subcommand. The bundled local `plugin-creator` validator continued to reject
the Codex manifest's intentional `hooks` field; that known validator conflict
remains an explicit non-pass rather than a reason to remove the declared hook.

## Known Limits

- `main` has no required status checks, zero required approvals, and no required
  code-owner review in the observed ruleset.
- No explicit branch-deletion rule was observed. Default-branch deletion
  behavior was not tested destructively and remains `UNAVAILABLE / NOT-RUN`.
- Exact collaborator membership and the effective release-tag creator roster
  were not collected.
- GitHub may hide bypass actors from callers without ruleset write visibility;
  the empty list was verified with the authenticated repository owner, while a
  lower-permission detailed bypass check was `NOT-RUN`.
- Repository-plan capability was not inferred. The two named rulesets were
  observed directly as active through GitHub's REST API.
- Manual re-verification remains necessary because a static repository check
  cannot detect remote ruleset drift.
