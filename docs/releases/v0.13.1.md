Version `0.13.1` publishes repository validation fixes with the same installed
runtime inputs as `0.13.0`.

## Current Routing Observations

The current optional observation contract uses `codex-core-v3`, observation
schema v3, and response schema V4. Its 20 cases cover all 10 public task routes,
including `clarify-intent`, `delegate-simple-task`, and `task-planning`.
Material ambiguity selects `clarify-intent` before an action route or explicit
delegation. Faithful current responses are no longer rejected by a route enum
that predates these skills.

The validator selects the contract from the record's version and benchmark
identity. Legacy schema v2 records keep their 17-case `codex-core-v2` contract
and response schema V3; mixed identities are rejected. Historical schemas,
corpora, and recorded results retain their original bytes and meaning.
Provenance, privacy, exact subject binding, mutation checks, and stopping at the
first failed or unknown case remain part of observation validation. See
[Routing Evaluations](../../evals/README.md#static-validation)
for the current contributor contract.

## Temporary Directory Compatibility

Historical replay now accepts a writable temporary-directory root reached
through a symbolic link, such as an existing `TMPDIR` alias. The newly created
temporary root is resolved before copying the historical tree. Existing link checks still apply within the copied tree, and replay leaves
the inspected source unchanged.

Contributors using such a temporary root no longer need to replace the alias
to run the historical validation checks. This correction does not change
installed plugin behavior or broaden replay write scope.

the repository-tooling corrections receive a patch package version while the
installed runtime contract remains identical to `0.13.0`. Repository policy
revision 35 records that exception and this release candidate. It does not
change version classification for later repository-only work.

`sha256:9a1ff3534fde91c79ab7972bbf2a8efedd56d58fe914ef82532385b942b54fc8`.
Skills, hooks, routing behavior, and action authority are unchanged. Existing
plugin workflows require no configuration changes. The canonical identity
and version policy remain in [Runtime and Repository Identity](../runtime-identity.md).
