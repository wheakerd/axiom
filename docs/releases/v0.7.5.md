# Axiom v0.7.5

Released: 2026-08-21

Version `0.7.5` adds a durable compatibility-evidence contract without
weakening Axiom's evidence boundary. Host observations now have a versioned
schema, an offline validator, an immutable release binding, explicit lifecycle
coverage, and privacy limits. Missing or unavailable cases remain visible
rather than being summarized as a pass.

The immutable Git tag `v0.7.5` will identify this release. Consumers that need
a stable source identity should use that tag rather than a moving alias or
floating branch.

## Highlights

### Compatibility evidence is machine-readable

`evidence/schema-v1.json` defines one exact six-case lifecycle matrix for each
host and platform record:

- fresh-session routed and no-route startup cases;
- manual-compaction routed and no-route cases; and
- automatic-compaction routed and no-route cases.

Every record identifies the immutable Axiom tag and 40-character commit, host
and version, operating system, architecture, shell, installation method,
expected and installed hook-command digests, sanitized requests,
expected and observed routes, mutation state, result, limitations, supporting
output, an anonymous reporter, and a UTC timestamp.

`scripts/check-compatibility-evidence.py` uses only the Python standard
library. It rejects duplicate JSON keys, unknown or missing fields, incomplete
lifecycle matrices, a passing result without matching route evidence, an
unavailable or not-run result that claims output, version or path drift,
current-release reuse of old evidence, and common sensitive-data patterns.

### Codex startup routing was observed on immutable v0.7.4

A disposable Linux `bubblewrap` view replaced the child process's Codex home
at its normal path. The existing authentication file was bound read-only and
was neither copied nor displayed; the real configuration and plugin cache were
not writable. Codex CLI `0.149.0` installed Axiom `0.7.4` from the local
immutable checkout, and the installed SessionStart command digest matched the
checked-in command.

Two separate ephemeral, read-only fresh sessions returned these minimal
sanitized results:

- the AGENTS architecture request selected `agents-architect` and reported the
  startup front door loaded; and
- the arithmetic control returned the expected answer and selected no Axiom
  route.

The record is bound to `v0.7.4` at
`ce34437e6ebf1cdaf5e55d40dc36e16c692875d5`. Manual and automatic Codex
compaction were not observed and remain `not-run`. The record is prior-release
evidence and is not carried forward as a v0.7.5 host pass.

### Current v0.7.5 host status is STATIC-ONLY

A Git commit cannot contain its own final object ID: adding that ID changes the
commit. `evidence/release-status.json` therefore leaves the not-yet-created
v0.7.5 commit binding null and marks both the checked-in release and Codex
current-host state `STATIC-ONLY` / `not-run`. Claude Code is `unavailable`
because no authenticated session or subscription was available.

After the immutable tag exists, a fresh-host record can bind to the exact tag
and commit and can be checked without editing the release tree:

```bash
python3 scripts/check-compatibility-evidence.py \
  --record axiom-v0.7.5-compatibility.json \
  --expected-tag v0.7.5 \
  --expected-commit <40-character-commit>
```

Such a record may be published as a content-addressed GitHub Release asset. It
supplements the checked-in `STATIC-ONLY` status; it does not rewrite that
status or make prior evidence current. Because a GitHub Release asset can be
replaced or deleted, reviewers should preserve the validator-reported SHA-256
and, when stronger provenance is needed, a separate signature or attestation.

## Compatibility and package shape

- Both plugin manifests declare version `0.7.5` and still point to
  `./skills/`.
- The seven direct public Skills and both platform-specific hook wrappers are
  unchanged in content and identity.
- The evidence files and validator are repository publication surfaces, not
  installed runtime dependencies.
- The release adds no installed file write, network request, background
  process, telemetry, credential access, or authorization expansion.

## Release validation

The release candidate was checked from a disposable copy outside the
publishable tree. The recorded workflow verified:

- distribution and publication agreement for 31 required files, 6 protected
  packaging JSON files, 64 Markdown files, 30 routing-contract fixtures, 56
  traceable-Git contract fixtures, 12 external-action gate fixtures, 10
  rollback gate fixtures, 4 source-linked cross-route and resume contracts, 17
  parser fixtures, version `0.7.5`, 5 manifest-schema fixtures, 3 hook-lifecycle
  fixtures, 15 release-tag fixtures, and 2 immutable Action pins;
- 2 immutable v0.7.4 compatibility records and 9 evidence-validator negative
  fixtures, with v0.7.5 remaining `STATIC-ONLY`;
- strict JSON parsing for both manifests, both marketplaces, both hook files,
  the evidence schema, release status, and both host records;
- Claude Code `2.1.220` strict plugin and marketplace validation; and
- English-only, brand-spelling, and whitespace checks.

The local `plugin-creator` validator still rejects the Codex manifest's
intentional `hooks` field. This is the same known validator discrepancy as the
prior release, not a pass; Axiom's publication validator, exact hook checks,
Codex local-marketplace installation, and Claude Code strict validation passed.
The Codex host observation remains limited to the two startup cases described
above. The Claude Code record preserves all six cases as `unavailable` and
contains no installed-hook or session claim.

## Known limits

- No checked-in v0.7.5 host record can bind to the final v0.7.5 commit. A
  post-tag release asset is required to make a same-release host observation
  available without creating another Git commit.
- Codex manual and automatic compaction reinjection, including routed and
  no-route post-compaction checks, remains `NOT-RUN`.
- Claude Code fresh startup, manual compaction, automatic compaction, routed,
  and no-route cases remain `UNAVAILABLE`; no pass is implied.
- The isolated Codex binary view did not expose the optional code-mode host.
  The tested prompts prohibited commands and did not rely on code mode.
- One host version and one Linux environment do not establish platform-wide
  compatibility.
