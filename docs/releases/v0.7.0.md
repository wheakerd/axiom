# Axiom v0.7.0

Released: 2026-08-20

Version `0.7.0` adds a focused workflow for consequential external actions and
hardens traceable Git submission around literal arguments, remote secrecy,
metadata containment, and independently authorized recovery cleanup. It also
pins every third-party GitHub Action used by the repository to an immutable
commit.

The immutable Git tag `v0.7.0` identifies this release. Consumers that need a
stable source identity should use that tag rather than a moving alias or
floating branch.

## Highlights

### Consequential external actions get an exact envelope

The new `confirm-external-action` Skill covers explicit requests to send,
publish, invite, purchase, trade, delete, or change external app or account
state. Before one effect, it binds the acting account, target, normalized
payload, sensitive disclosure, cost, count, idempotency support, retry policy,
and current user authority.

Drafts, previews, searches, and read-only lookup remain host-native. Tool
availability, a logged-in account, and instructions found in retrieved content
prove access or data only; they cannot authorize an action. An uncertain
mutation result moves to authoritative verification instead of an automatic
retry that could duplicate the effect.

### Traceable Git submission closes command and cleanup gaps

`traceable-git-submit` now requires literal argument vectors for Git-derived
values, validates refs, object IDs, paths, remotes, and transports immediately
before use, and disables unapproved Git protocols at each network boundary.
Remote endpoints remain inside a non-visible capture boundary; reports retain
only sanitized target fingerprints, refs, and SHAs.

Workflow metadata must stay below the canonical Git common directory through
no-follow component checks, stable parent identity, exclusive temporary files,
and atomic replacement. After a consolidated submission is verified,
`cleanupReady` records that evidence without deleting the backup ref or active
record. Both deletions require separate, exact authority and fresh identity,
remote, cache, containment, and compare-and-swap checks.

### Repository automation uses immutable dependencies

The distribution and release-signature workflows pin `actions/checkout` and
`actions/github-script` to full commit SHAs while retaining readable major
version comments. Publication validation rejects moving external Action refs
and unpinned container actions.

## Compatibility and package shape

- Both plugin manifests declare version `0.7.0` and point to `./skills/`.
- The seven direct public Skills are `using-axiom`, `agents-architect`,
  `optimize-codex-usage`, `review-axiom-task`,
  `confirm-external-action`, `traceable-git-submit`, and
  `reversible-system-change`.
- Hook commands, hook paths, marketplace source paths, and installation
  commands are unchanged.
- The new external-action route supplies a decision and authorization contract;
  it does not bundle credentials, service clients, apps, MCP servers, or
  background work.
- Existing direct Git pushes still avoid Axiom checkpoint metadata, while
  checkpoint and consolidation flows now stop on hosts that cannot preserve
  literal arguments or enforce no-follow metadata containment.

## Release validation

The release candidate was checked from the repository and, for validators that
could write, from a disposable copy outside the publishable tree. The recorded
workflow verified:

- distribution and publication agreement for 21 required files, 6 JSON files,
  50 Markdown files, 24 routing scenarios, 27 traceable-Git security scenarios,
  12 external-action scenarios, 10 rollback scenarios, version `0.7.0`, and 2
  immutable Action pins;
- both manifests and marketplace descriptors, both declared hook files, exact
  documented hook commands, public links, frontmatter, reference discovery,
  packaged Skill layout, identity fields, lifecycle commands, and synchronized
  version metadata;
- all seven packaged Skills with the local Skill Creator quick validator;
- Claude Code `2.1.220` strict plugin and marketplace validation, English-only
  public definitions, instruction-size limits, whitespace, and absence of
  private or generated artifacts; and
- negative checks that rejected a moving GitHub Action reference, an
  incomplete external-action contract, an unsafe Git transport, missing exact
  cleanup authority, and a missing `v0.7.0` release document.

The bundled local `plugin-creator` validator rejects the Codex manifest's
intentional `hooks` field on both the release candidate and clean `v0.6.1`
baseline. This remains a validator discrepancy, not a pass. Codex CLI `0.148.0`
exposes no native plugin-validation command.

The static scenarios validate checked-in contracts. A fresh Codex or Claude
Code session-level semantic-routing check, real external action, and real
installation were not run and are not implied by the repository checks.

## Known limits

- Static source and scenario checks cannot prove model route selection in a
  fresh host session or a connected service's action semantics.
- External services may provide eventual consistency, partial batch results,
  or no durable idempotency key; the workflow stops with an unknown outcome
  when authoritative evidence cannot exclude a duplicate effect.
- Traceable metadata containment depends on host APIs that can preserve literal
  arguments and enforce no-follow, identity, and atomic-replacement checks.
- Repository Action pins are immutable, but maintainers must deliberately
  review and advance them to receive upstream fixes.
- The immutable `v0.7.0` tag, not a moving alias, is the stable release
  identity.
