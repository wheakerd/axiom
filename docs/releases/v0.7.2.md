# Axiom v0.7.2

Released: 2026-08-20

Version `0.7.2` closes the authorization, Git ref-mutation, metadata-validation,
resume, and release-target gaps identified after `v0.7.1`. It adds no public
Skill and does not broaden ordinary edit, push, deployment, deletion, or
credential authority.

The immutable Git tag `v0.7.2` identifies this release. Consumers that need a
stable source identity should use that tag rather than a moving alias or
floating branch.

## Highlights

### One Git request cannot widen into unrelated ref mutations

`traceable-git-submit` now treats remote refresh and network push as independent
authorization axes. Refresh fetches one validated source ref without configured
refspecs, pruning, tags, submodules, `FETCH_HEAD`, maintenance, or commit-graph
writes, then compare-and-swap updates only the frozen tracking ref. Push uses
one frozen target and one full-ref refspec while disabling followed tags,
recursive submodule pushes, push signing, configured push options, upstream
setup, force modes, and unapproved pre-push hooks.

Git object validation derives its width from the repository's frozen `sha1` or
`sha256` format. Backup refs use a create-only null-OID transaction, so a
concurrent ref cannot be silently replaced.

### Routing and resumed execution fail closed

Clear Axiom provenance can identify ownership and routing, but it no longer
substitutes for current user authority to edit an instruction system. The
startup gate now selects both `confirm-external-action` and
`reversible-system-change` when a persistent change also publishes, deletes, or
otherwise mutates external state, while keeping their authorization gates
independent.

After resume or compaction, an active external or persistent operation performs
zero new mutations unless the phase, exact authority, action envelope, prior
attempts, idempotency state, write set, and rollback evidence can be rebuilt
from host-native context and current owning-system evidence. An unknown
external result enters verification only and is never resent automatically.

### Publication guards parse the protected structures they certify

The publication guard now consumes the complete bounded schema for every Skill
frontmatter and `agents/openai.yaml` file, rejects duplicate, unknown,
ill-typed, or trailing content, and structurally closes alternate GitHub Action
`uses` spellings instead of ignoring them. The current release-note path and
README, changelog, and compatibility references are derived from the release
version.

The release signature workflow runs for same-repository pull requests into
`main`, `main` and `v*` tag pushes, and published or edited GitHub Releases. It
requires a pull-request head to descend from the current default branch, peels
annotated tags to a commit, requires release targets to be on `main`, and
requires a valid signature made with GitHub's signing key. Its manual entry
point can verify the exact signed `release/v*` candidate before that trigger is
present on the default branch.

## Compatibility and package shape

- Both plugin manifests declare version `0.7.2` and point to `./skills/`.
- The seven direct public Skills and both platform-specific hook wrappers are
  unchanged in number and identity.
- Existing `0.7.1` installations remain compatible; the host controls when a
  newer installed snapshot becomes active in a session.
- The release adds no implicit edit, commit, push, fetch, deployment, restore,
  promotion, cleanup, telemetry, update, or background-work authority.

## Release validation

The release candidate was checked from the repository and, for validators that
could write, from a disposable copy outside the publishable tree. The recorded
workflow verified:

- distribution and publication agreement for 23 required files, 6 JSON files,
  52 Markdown files, 30 routing-contract fixtures, 56 traceable-Git contract
  fixtures, 12 external-action gate fixtures, 10 rollback gate fixtures, 4
  source-linked cross-route and resume contracts, 16 parser fixtures, version
  `0.7.2`, and 2 immutable Action pins;
- both manifests and marketplace descriptors, both declared hook files, exact
  documented hook commands, public links, strict protected YAML schemas,
  packaged Skill layout, lifecycle commands, and synchronized version
  metadata;
- all seven packaged Skills with the local Skill Creator quick validator;
- Claude Code `2.1.220` strict plugin and marketplace validation, English-only
  public definitions, instruction-size limits, whitespace, and absence of
  private or generated artifacts;
- disposable Git `2.55.0` behavior for exact no-prune refresh, closed one-ref
  push, no followed tag, unapproved-hook bypass, SHA-256 OIDs, and atomic
  create-only backup-ref collision handling; and
- negative copies that rejected malformed Skill frontmatter, malformed agent
  metadata, alternate moving Action syntax, and a missing current release
  document, plus twelve release-workflow signature, ancestry, and event cases.

The bundled local `plugin-creator` validator rejects the Codex manifest's
intentional `hooks` field. This remains a validator discrepancy, not a pass;
Claude Code strict validation and Axiom's direct manifest and hook checks pass.

## Known limits

- Static contract fixtures do not prove model route selection in a fresh host
  session or the semantics of a connected service.
- Codex Security Deep Scan was not run because the available session lacked its
  required managed filesystem permission profile; no Deep Scan result is
  implied.
- Dynamic Git probes ran on Linux with Git `2.55.0`; other supported operating
  systems and Git versions rely on the documented version-aware stop boundary.
- A fresh installation, fresh-session route-selection test, real external app
  action, and real persistent system change were not run.
- The immutable `v0.7.2` tag, not a moving alias, is the stable release
  identity.
