# Axiom v0.4.0

Released: 2026-08-10

Version `0.4.0` reduces Axiom's Codex context and workflow overhead while
preserving its authorization, rollback, safety, and completion-evidence
boundaries. It adds one explicit usage-optimization route and keeps ordinary
coding, documentation, explanation, and status work outside Axiom.

The immutable Git tag `v0.4.0` identifies this release. The moving `latest`
Git tag and GitHub's Latest Release marker are synchronized to the same release
commit; consumers that need a stable identity should use `v0.4.0`.

## Highlights

### Explicit Codex usage optimization

The new `optimize-codex-usage` Skill triggers only when a user explicitly asks
to reduce or diagnose Codex credits, tokens, context, Skill/AGENTS/MCP loading,
tool churn, validation overhead, or reporting cost. It preserves the requested
quality and safety bar, labels repository measurements as proxies, and does not
claim access to hidden token, credit, reasoning, or cache data.

### Smaller startup and active routes

The session-start `using-axiom` gate now owns only route selection, startup
safety, no-match behavior, and explicit refresh discovery. Marketplace update
detail moved to an on-demand reference.

AGENTS Architect no longer loads forwarding indexes. Its remaining references
are directly discoverable from the parent Skill, and validation scales with the
changed route rather than a fixed broad scenario matrix.

Traceable Git Submit separates direct history-preserving push from checkpoint
metadata, local consolidation, combined submission, and recovery. Reversible
System Change separates read-only planning from execution and loads execution
guidance only after current rollback evidence and action authority pass.

### Preserved trust boundaries

Route selection still does not authorize edits, commits, pushes, deployments,
deletion, credential use, or promotion. Startup hooks remain foreground-only
and read-only, with no background service, telemetry, automatic update, or
network check. Both platform wrappers continue to use one shared `skills/`
source.

## Compatibility and package shape

- Both plugin manifests declare version `0.4.0` and point to `./skills/`.
- The direct public Skills are `using-axiom`, `agents-architect`,
  `optimize-codex-usage`, `traceable-git-submit`, and
  `reversible-system-change`.
- Codex and Claude Code retain separate manifests, marketplace descriptors,
  and hook files over the same Skill source.
- No platform-specific Skill copy, runtime dependency, service, daemon,
  watcher, telemetry path, or automatic updater was added.

## Release validation

The release candidate was checked from the repository and, for validators that
could write, from a disposable copy outside the publishable tree. The recorded
workflow verified:

- distribution agreement among the Skill tree, both manifests, both
  marketplace wrappers, and the README shared-skill list;
- publication invariants for required files, JSON structure, manifest version
  agreement, exact hook shapes, documented hook commands, Markdown links,
  frontmatter, reference discovery, and packaged Skill layout;
- ten static route-contract scenarios and ten rollback-gate scenarios;
- JSON and YAML parsing, English-only public definitions, instruction-size
  limits, whitespace, and absence of private or generated artifacts;
- all five packaged Skills with the local Skill Creator quick validator; and
- strict Claude Code `2.1.220` plugin validation.

Codex CLI `0.147.0` did not expose a plugin-validation command. The bundled
local `plugin-creator` validator rejected the Codex manifest's intentional
`hooks` field even though Axiom's checked-in wrapper and publication validator
require it. This remains a validator discrepancy, not a pass.

The static routing scenarios validate checked-in trigger, load-chain, no-match,
and authorization contracts. They do not prove that a fresh host model will
make the same semantic selection. Exact tokens, credits, reasoning work, and
cache hits remain unavailable unless a host exposes them for a scoped run.

## Known limits

- Existing installations and sessions may retain earlier marketplace or hook
  state until the user explicitly refreshes and starts a new session.
- Hook presence does not prove host trust, lifecycle delivery, or runtime
  execution; users should compare installed commands with the README.
- Axiom cannot turn an unavailable validator or downstream observation into a
  pass.
- The moving `latest` tag is a convenience alias, not an immutable source
  identity.
