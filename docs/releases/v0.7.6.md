# Axiom v0.7.6

Released: 2026-08-21

Version `0.7.6` separates pull-request tree validation from release provenance.
It is a compatible repository-security fix for
[Issue #26](https://github.com/wheakerd/axiom/issues/26); it adds no public Skill
and does not broaden any installed route or action authority.

The immutable Git tag `v0.7.6` will identify this release. Consumers that need
a stable source identity should use that tag rather than a moving alias or
floating branch.

## Highlights

### Pull requests validate proposed trees

`Distribution and publication guards` owns pull-request validation for
same-repository and fork contributions targeting `main`. It checks the proposed
merge tree with the distribution, compatibility-evidence, and publication
validators without requiring the contributor's head commit to be signed by
GitHub or to originate in the `wheakerd/axiom` repository.

The workflow uses the ordinary `pull_request` event, grants only
`contents: read`, leaves every unlisted token permission at `none`, does not
reference repository secrets, and sets `persist-credentials: false` for
checkout. Its steps run exact repository-local validators and contain no
publication or write-token path.

### Release provenance starts at protected history

`Release signature guard` no longer receives pull-request events. It continues
to check pushes to `main`, strict `v*` tag events, published or edited GitHub
Releases, and manual runs limited to `main` or a versioned
`release/v<semver>` candidate. The exact target must use the matching versions
from both manifests, remain on approved `main` history, and carry a valid
signature made with GitHub's signing key.

Tag movement, deletion, forced updates, malformed tags, manifest-version
mismatches, targets outside `main` history, and GitHub Release event/tag
mismatches remain fail-closed cases. Active GitHub rulesets remain the
server-side prevention layer for unsigned `main` updates and release-tag
mutation; the workflow independently verifies the resulting provenance.

### Deterministic fixtures preserve the trust split

The publication validator now models the static portions of all eight Issue
#26 scenarios:

1. a valid same-repository pull-request tree;
2. a valid unsigned fork pull-request tree;
3. a fork tree rejected for a publication-policy violation;
4. an unsigned push to `main` rejected by provenance;
5. a valid strict release tag on approved history;
6. a tag outside approved `main` history rejected;
7. tag movement, deletion, and forced-update attempts rejected; and
8. a GitHub Release whose event ref does not match its tag rejected.

Additional fixtures preserve malformed-tag, manifest-version, manual-candidate,
GitHub-signature, and mutation-gate regression coverage. These are offline
workflow and event-graph checks, not evidence that GitHub scheduled a real fork
run.

## Compatibility and package shape

- Both plugin manifests declare version `0.7.6` and point to `./skills/`.
- The seven direct public Skills, both marketplace wrappers, and both
  platform-specific hook wrappers are unchanged in content and identity.
- The change affects repository validation and release publication only. It
  adds no installed file write, network request, background process, telemetry,
  credential access, route-selection change, or authorization expansion.
- `evidence/release-status.json` marks v0.7.6 `STATIC-ONLY`. Immutable v0.7.4
  host observations remain prior-release evidence and are not promoted to a
  current v0.7.6 pass.

## Release validation

The release candidate was checked from a disposable copy outside the
publishable tree. The recorded local workflow verified:

- distribution, compatibility-evidence, and publication agreement, including
  strict JSON and YAML parsing, synchronized manifest versions, public links,
  immutable Action pins, hooks, packaged Skill layout, and release-document
  surfaces;
- the exact read-only pull-request workflow shape, including permissions,
  credential persistence, secret references, immutable checkout, and exact
  validator commands;
- three pull-request event-graph fixtures plus the exact release-workflow
  JavaScript against positive and negative main, tag, Release, and manual-run
  scenarios; and
- preservation of signature, strict-tag, tag-mutation and deletion, ancestry,
  manifest-version, and GitHub Release ref failure paths.

The bundled local `plugin-creator` validator still rejects the Codex manifest's
intentional `hooks` field. This remains a known validator discrepancy, not a
pass. Claude Code host validation was unavailable because the current user has
no Claude Code subscription or authenticated session; no Claude Code host pass
is implied.

## Known limits

- A real fork pull-request run was not created for this release. GitHub
  scheduling, first-time-contributor approval, fork-token behavior, and runner
  execution therefore remain `NOT-RUN` until observed on an actual
  contribution.
- `actionlint` was unavailable in the validation environment and remains
  `NOT-RUN`; the repository's strict YAML parser and deterministic workflow
  fixtures were used instead.
- No fresh v0.7.6 Codex host session was run. The immutable v0.7.4 Codex startup
  observations remain prior-release evidence only, with compaction still
  `NOT-RUN`.
- Claude Code startup, manual compaction, automatic compaction, routed, and
  no-route cases remain `UNAVAILABLE`; no subscription was available and no
  pass is implied.
- The release pull request, merged-`main` run, immutable-tag run, and GitHub
  Release run are remote publication evidence and are not claimed by local
  deterministic checks.
- The immutable `v0.7.6` tag, not a moving alias, is the stable release
  identity.
