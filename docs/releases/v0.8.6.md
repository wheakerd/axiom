Version `0.8.6` is the contiguous patch release for [Issue #57](https://github.com/wheakerd/axiom/issues/57). It joins Axiom's signed release target, content-addressed routing observation, repository-owned validator, durable attestation, and GitHub immutable-release state without changing installed Skills, hooks, route selection, or action authority.

## Exact Draft Evidence Validation

The new `Publish immutable release` workflow is manual and main-only. It accepts one strict `v<major>.<minor>.<patch>` tag, checks out the exact dispatch commit, requires that tag to resolve to the same commit, and serializes every repository-wide Latest publication rather than only runs for one tag. It grants only `contents: write`, persists no checkout credential, uses no secret expression or arbitrary repository/ref input, and pins checkout plus Python setup to full Action commits.

Before any asset or Release mutation, and again immediately around publication, the workflow reads the repository immutable-release setting, default branch, live `main`, live tag target, REST signature verification, GraphQL signature verification, and current GitHub Latest Release. It requires immutable releases to remain enabled, the default branch to remain `main`, `main` and the tag to resolve to the checked-out commit, and the commit to carry a valid GitHub-made signature. It rejects a different Latest tag at an equal or newer numeric SemVer, preventing an older dispatch from regressing the repository-global Latest marker.

The workflow uniquely selects one authenticated Release-list entry named `Axiom v0.8.6`, freezes its numeric Release ID, and uses only ID-addressed reads, uploads, and publication after selection. A new draft starts with exactly one uploaded `axiom-v0.8.6-codex-core-v2-<full-sha256>.json` asset. The workflow downloads that asset through the GitHub API and validates:

- the Release body exactly matches this checked-in version document;
- the full SHA-256 in the filename against the downloaded bytes;
- the GitHub asset ID, state, byte count, timestamps, and exposed SHA-256 digest;
- the exact version, tag, signed release commit, and tree;
- schema v2, response schema V3, and the fixed 17-case benchmark order;
- one fresh call per case, 17/17 `PASS`, no retry or unavailable suffix; and
- zero canonical false negatives, high-impact false positives, clarification mismatches, mutation attempts, tool events, or protected-snapshot changes.

The observation still passes through the existing external mode in `scripts/check-publication.py`; the release workflow does not redefine that acceptance contract.

## Durable Attestation And Immutable Publication

After validation, `scripts/check-release-evidence.py` emits one deterministic minimal JSON attestation. Its content binds the Release ID, version, tag, commit, tree, release-notes SHA-256, observation asset ID, name, size, SHA-256, GitHub digest, and validator result. The attestation filename exposes the full SHA-256 of its own bytes.

The workflow uploads the attestation to the frozen Release ID without replacement, re-reads the draft by ID, downloads the remote attestation bytes, and requires both assets to match their filenames, IDs, sizes, and API digests. If a prior run already uploaded the exact deterministic attestation, a rerun downloads and verifies it instead of replacing it. If publication already succeeded but final verification was interrupted, a rerun performs final-only readback without attempting another mutation.

The workflow then publishes that same draft as GitHub Latest, re-reads both the final Release and Latest endpoint, downloads both final assets again, and requires:

- `draft=false` and `prerelease=false`;
- `immutable=true`;
- the same Release, tag, target commit, title, observation asset, and attestation asset as the pre-publication snapshot; and
- the Latest Release ID and tag to match v0.8.6.

A missing, duplicate, malformed, replaced, or digest-mismatched asset stops the workflow. An incomplete, non-pass, retrying, mutating, wrong-case-set, or wrong-subject observation also stops through the existing external validator.

## Repository Capability And Limits

On 2026-08-26 UTC, the authenticated repository-owner API enabled immutable releases for `wheakerd/axiom`. Immediate read-back reported `enabled: true` and `enforced_by_owner: false`. GitHub applies that setting only to future Releases; v0.8.5 and earlier Releases remain in their previous mutable state.

The workflow checks the live repository setting before its first mutation, immediately before publication, and after publication. Its final check uses the Release response rather than inferring immutability from a local file.

GitHub documents immutable Release protection for the associated tag and uploaded assets. It does not document the title, body, Latest selection, or the Release object itself as immutable. Axiom therefore binds the exact title and release-notes SHA-256 into the durable attestation and fails later readback on metadata drift; that is detection, not a claim that GitHub prevents every metadata edit or Release deletion.

## Separate Provenance Owners

`Release signature guard` and its stable `Verify GitHub-signed release target` check are unchanged. They continue to own the tag target, manifest version, `main` history relationship, and GitHub-made commit signature. Because GitHub does not start another workflow for ordinary events created with a workflow's `GITHUB_TOKEN`, the publication workflow also fails closed on direct REST and GraphQL signature readback. After publication, the release operator explicitly dispatches the unchanged signature guard on the exact tag and requires that independent run to pass. `Publish immutable release` separately owns the downloaded evidence bytes, durable attestation, final asset set, immutable Release state, and Latest identity.

Neither check edits historical evidence. Terminal `FAIL`, `UNKNOWN`, `NOT-RUN`, and `UNAVAILABLE` records remain immutable and are not promoted by a new Release asset.
