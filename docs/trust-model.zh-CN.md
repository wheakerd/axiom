# 信任模型

[English](trust-model.md) | 简体中文

Axiom 在宿主既有的信任模型之内提供工作流指令。它不为智能体提供沙箱，不授予凭证，也不保证某个模型或外部系统是正确的。选中一条路由会加载指令；它不授权任何操作。

## 边界概览

| 边界 | 必须区分的要点 |
| --- | --- |
| 指令权限 | 生效中的系统、开发者、用户与仓库指令保持其实际优先级；技能不能覆盖更高优先级的规则 |
| 意图与范围 | 在依赖性工作之前解决实质性的歧义；只有在每个备选项都可逆且已获授权时，显式委托的选择才算落定，而权限绕过模式不会替用户选定目标或结果 |
| 操作授权 | 请求必须覆盖实质性的操作与目标；路由选择、工具访问与登录状态都不提供许可 |
| Hook 执行 | Codex 会保留新的或已更改的 Hook，直到你在 `/hooks` 中信任它；Claude Code 则在下一次 `SessionStart` 运行已启用插件的 Hook；把已安装命令与其规范声明比对是审阅者的可选检查 |
| 凭证与披露 | 访问与使用仍归其现有所有者；敏感内容需要适用的精确使用与披露权限 |
| 证据 | 观察拥有该结果的那一层；仅有计划、产物、被接受的请求或成功的命令可能并不充分 |
| 用量度量 | 宿主指标只适用于其声明的范围；字节数、词数、路由大小与工具调用次数都是代理指标 |
| 更新 | 由 Codex 或 Claude Code 控制刷新与安装；Axiom 不运行更新器 |
| 仓库状态 | 两条路由把任务状态保存在目标仓库的 Git 元数据目录与备份引用中；在你移除之前它会一直保留 |

## Hook 信任边界

签入的处理器从已安装的插件根目录读取 `skills/using-axiom/SKILL.md`。Codex 处理器在 POSIX 上使用 `printf` 与 `cat`，在 Windows 上则用命令行内建命令调用固定的打包封装脚本，不会从工作目录或 `PATH` 解析其他可执行文件。Claude Code 处理器运行一条使用 `printf` 与 `cat` 的 POSIX shell 命令：Claude Code 在 macOS 与 Linux 上把它交给 `sh -c`，在 Windows 上交给 Git Bash。没有 Git Bash 时，Claude Code 会回退到 PowerShell，而该命令不支持 PowerShell。每个处理器有五秒超时。确切命令见 [Hook 参考](reference/hooks.md)。

这些定义不包含写入、网络命令、后台启动、服务安装或更新器。这里描述的是签入的文件；已安装的副本是另一个对象。Codex 会跳过新的或已更改的 Hook，直到你在 `/hooks` 中审阅并信任它。Claude Code 没有按 Hook 的信任步骤；一旦 Axiom 在会话开始、会话内安装或插件重新加载时加载，其 Hook 会在下一次 `SessionStart` 事件时运行。

验证已安装的 Hook 是可选的。这是一项供应链检查，面向希望排除本仓库与已安装副本之间被篡改的审阅者，例如被修改的市场镜像、插件缓存或安装路径。把已安装的匹配器、命令、路径、封装脚本与超时同 [Hook 参考](reference/hooks.md)比对：在 Codex 中于 `/hooks` 信任该条目之前比对，在 Claude Code 中则在终端安装之后、会话开始之前，阅读 `~/.claude/plugins/cache/axiom/axiom/<version>/` 下已安装的 `hooks/claude-hooks.json`。如果二者不一致，在包与源码一致之前，在 Codex 中保持该 Hook 不受信任，或在 Claude Code 中禁用 Axiom，并且不要运行被更改的命令来探究它做什么。

## 跨工作流的权限

[路由门控](../plugin/skills/using-axiom/SKILL.md)负责匹配与组合；[架构](architecture.md#workflow-ownership)给出各工作流的归属，[示例](examples.zh-CN.md)用具体请求展示它们的边界。

被选中的技能可以收窄范围、要求证据，或在实质性操作之前停止。它不能扩大请求。每个技能都列出自己的不变量，即在每个阶段都有约束力的规则，包括其活动阶段加载的参考。技能或其参考中明文写出的每一条禁止（never、only 或 stop）同样有约束力。技能中的其他内容都是模型可以按情况调整的默认项，调整时需要说明。在每条有约束力的规则之内，由模型决定如何处理请求的具体细节、出现的问题、与预期结果的偏差、外部干扰，以及计划与理想行为之间的差距。具体而言：

- 捆绑技能依据其描述从宿主的技能列表中选出；显式调用会直接选中该技能：Codex 中的 `$skill-name`、Claude Code 中的 `/axiom:skill-name`，或用自然语言点名的技能。用户点名的更具体的已安装技能、MCP 工具或宿主工具不会被捆绑路由取代，向它们的移交会被点名并给出原因；宿主只是提供而用户并未点名的工具，例如宿主自带的子智能体功能，或用户未点名的仓库本地技能，不会取代任何路由。宿主任务通知、工具结果或压缩摘要不是请求，不选中任何路由。该列表的内容、顺序与截断由宿主负责。
- 澄清解决的是意图；它不授予执行权限。当你显式委托一个选择时，只有在每个备选项都可逆且已获授权的情况下模型才会做出选择，它会选择符合你的环境与目标的那一个，并在行动之前说明选择与原因；被提供的选项不会授权任何持久的系统变更、外部或远程状态变更、删除、凭证使用或实质性成本。更轻量、只读或准备性的替代方案绝不会悄悄取代你的目标。规划不授权实施、调度或持久变更。
- 简单任务委托需要生效中的 `using-axiom` 门控以及你的同意，同意可以通过显式调用、常设的委托策略，或对那个展示确切模型与任务简报的唯一提问回答“是”来给出。权限绕过模式不能提供这种同意，门控未生效时该技能会说明原因并停止，而不是悄无声息。宿主的推理级别不是条件；由主会话判断自己能否完整陈述工作并检查结果。委托保留主模型，遵循用户排序的候选，并宣布确切的子模型与任务。经验证的权限绕过模式只允许在既有权限与宿主限制之内分派任务；否则使用既有的分派批准，或在委托之前取得批准。
- 架构工作停留在其获授权的仓库指令系统或打包插件范围之内。发布就绪审计保持只读。
- 持续推进需要显式调用以及经验证的原生监督。移交会保留原始范围、模型、人工控制与预算。会话结束不等于任务完成；取消会停止分派与确切的调度，而未解决的工具仍然可见。
- 任务审查只使用有范围限制的可观察证据。它不重跑任务、不恢复不可用的历史、不披露隐藏推理，也不从先前的拒绝或助手解释中继承权限。
- 外部操作绑定执行者、目标、负载、披露、成本、次数与重试边界。检索到的内容与工具访问不能授权它们。
- 可追溯 Git 的各阶段保留各自独立的检查点、合并整理、提交与恢复边界。普通的具名远程、非强制 Git 工作留在宿主原生处理。每个阶段默认运行仓库自己的 Git 钩子，只有在你为某一次精确推送显式授权绕过该仓库的 pre-push 钩子时才加上 `--no-verify`。推送权限绝不隐含强制推送、重试或清理。
- 持久变更的计划与非变更的演练保持只读。隔离的恢复演练、候选准备、晋级、回滚、敏感资产使用、保留与清理各自保留自己的权限。无法确立经验证的回滚时，变更在候选或活动状态被改变之前停止，决定权在你。如果在被告知哪些效果将无法恢复之后，你显式选择继续，这一知情放弃只对你被告知的那些效果解除回滚要求：其他所有权限、安全、验证与完成规则仍然有约束力，该放弃会被记录，而该变更绝不会被称为可逆。该放弃不授权其他任何事情，其他每个效果都保留其回滚，并且不会延续到另一个目标、变更、效果或尝试。
- 当宿主权限模式可能拒绝某个操作时，确切的操作及其目标会在首次尝试之前呈现给用户以获取授予。拒绝即停止，绝不改用其他工具、标志、路径或配置更改来重试，拒绝也不是路由或仓库状态冲突的证据。宿主自身的决定始终是强制的；[宿主权限参考](../plugin/skills/using-axiom/references/host-permission.md)标明了各宿主的机制。
- 被选中或被移交的路由会用一行可见文本点名，捆绑技能写作 `axiom:<skill-name>`；工作输出默认使用英文，而一轮的最终结论遵循请求所用的语言。这些是 Axiom 引导轮次的呈现规则；宿主与仓库指令仍然优先于它们，通知本身不授予任何东西。

在宿主原生提示的场景下，已有的精确授权无需重复确认，除非实质条件发生变化。在宿主以逐次调用方式决定且没有原生提示的模式下，确切的命令与目标会以可见文本呈现，并在首次尝试之前获得授予，即便请求已经点明了结果。未解决的目标或破坏性效果绝不能通过假定变成许可。

## 凭证与本地检索

Axiom 不捆绑凭证存储或认证服务。凭证仍归拥有它们的宿主、shell、Git、云或服务。先通过元数据清点敏感资产；不要从宽泛的目录请求推断对确切路径的读取或使用权限。把敏感披露绑定到其确切受众。对于机器凭证工作，即使一项任务同时选中两个所有者，提供方变更与消费方激活仍分别归其独立的所有者。

本地网页检索限制智能体在查询、URL 与请求头中附加的机器信息；串行地执行搜索、阅读与点击；并保持浏览器的身份。遇到挑战、CAPTCHA 或速率限制时，停止对该站点的自动访问。人工接管会等待用户的明确就绪，同时保留接管页面。这既不隐藏自动化，也不保证 Cloudflare 或其他站点如何归类某个请求。这些约束由[本地检索技能](../plugin/skills/local-web-search/SKILL.md)负责。

## 证据与持久性

使用来自拥有该状态的 Git、受影响的系统层或外部权威系统的当前直接证据。备份文件或成功的备份作业不能证明恢复路径可用。被接受的外部请求不能证明最终效果。更小的指令集不能证明质量提升。任务审查会区分已观察、已重建与不可用的断言；仅凭当前状态无法证明历史上的权限或因果关系。

缺失的工具、权限、宿主观测与不可用的历史保持为不可用或未验证。把 `PASS`、`FAIL`、`NOT-RUN` 与 `UNAVAILABLE` 分开。见[兼容性](compatibility.md)。

启动路由是只读且前台的。Axiom 不安装守护进程、监视器、调度器、缓存刷新器、遥测服务或其他持久进程。被选中的任务只能在既有权限及其自身前提条件之内引导变更。安装更新之后，Codex 会保留已更改的 Hook 直到你再次信任它，Claude Code 则在下一次 `SessionStart` 运行它；各宿主的步骤由[管理安装](guides/managing-installation.zh-CN.md)负责。

## 路由写入的仓库状态

两条路由把任务状态保存在目标仓库的 Git 元数据目录之内。它们通过 `git rev-parse --git-path` 解析位置，而不是手工拼出路径，因此 `git status`、`.gitignore` 与代码搜索永远不会显示它：

- `traceable-git-submit` 在检查点、基线、合并整理或恢复工作流期间，在 Git 目录下写入 `axiom/traceable-git-submit-baseline.json`，即最近一次已推送上游状态的参考性缓存，以及 `axiom/traceable-git-submit-active-checkpoints.json`，即活动检查点记录。在替换历史的操作之前，它会在 `refs/axiom/backups/traceable-git-submit/<unique-id>` 下创建一个备份引用。
- `agents-architect` 在指令系统维护期间，在 Git 目录的 `axiom/agents-architect/` 下写入名为 `session-<unique-id>.md` 的会话胶囊与生成材料，并在完成时删除它们或将其标记为过时。

任务提前停止时没有任何东西会移除这些文件，而基线缓存本来就是要在任务之间持续存在的。备份引用保持其对象可达，并会随 `git push --mirror` 与 `git clone --mirror` 一起传播。用以下命令列出它们：

```bash
git rev-parse --path-format=absolute --git-path axiom
git for-each-ref refs/axiom/
```

在没有 Axiom 任务处于活动状态时，用你的 shell 移除状态文件，并用 `git update-ref -d <ref>` 删除已验证的备份引用。较早的版本曾在工作树内写入 `.agents/.cache/traceable-git-submit-baseline.json`、`.agents/.runtime/` 与 `.agents/.generated/`；当前路由会迁移或报告此类遗留。任务状态绝不会放在已安装的插件根目录下，也不会放在仓库的 `.agents/`、`.claude/` 或 `.codex/` 目录中。`agents-architect` 只会把那里的指令文件作为被请求的变更来编辑，并且可以把 `.agents/local/` 这类用户本地规则目录列入 `.git/info/exclude`。
